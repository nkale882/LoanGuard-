# Loan Approval Governance Demo (Knowlytix)

A notebook-first educational example of applying Knowlytix governance components to a synthetic loan policy and sample application cohort. The deterministic path uses no hosted LLM. Optional Groq integration is isolated in notebook 03.

> All policy text and applicant records in this project are synthetic. A route marked eligible means only that the application satisfies the demo's listed pre-screen thresholds and may proceed to human underwriting. This project does not approve, decline, price, or recommend real loans. A failed threshold is rejected from the automatic pass path and sent to manual review; missing or invalid inputs are marked REVIEW. Neither result is an automatic loan decline.

## Project contents

- `loan_policy.md` — synthetic policy source ingested into Knowlytix GMS.
- `synthetic_applications.csv` — 12 illustrative applications and expected routing labels.
- `loanguard.py` — reusable ingestion, typed claim, screening, policy, tracing, and evidence functions; also provides a command-line walkthrough.
- `notebooks/00_start_here.ipynb` — project map and run instructions.
- `notebooks/01_loan_approval_governed_walkthrough.ipynb` — policy ingestion, typed verification, application routing, action gates, audit integrity, compliance evidence, and lineage.
- `notebooks/02_fairness_and_human_review.ipynb` — group counts and a field-invariance smoke check with explicit limitations.
- `notebooks/03_groq_provider_setup.ipynb` — optional Groq catalog lookup, LiteLLM setup, generated response, and Knowlytix claim gates. Live calls may consume provider quota.
- `notebooks/04_gms_graph_visualization.ipynb` ? complete triple inventory and an orbitable 3D Plotly graph with zoom and hover details.
- `loan_store/` — local Knowlytix GMS cache generated by the installed library.
- `out/` — audit and compliance artifacts generated by the command-line run.

## Requirements and setup

Use the Python 3.12 environment that has Knowlytix and its dependencies installed, then open this project in Jupyter with that environment's kernel. The deterministic notebooks use the local policy and do not need an API key. Notebook 04 uses Plotly; install it in the selected Jupyter environment with `python -m pip install -r requirements-visualization.txt` if it is not already available.

For the optional Groq notebook, set `GROQ_API_KEY` in a local `.env` file or process environment. The `.env` file is ignored by Git; never paste a key into a notebook or commit it. Optionally set `KNOWLYTIX_GROQ_MODEL` to an exact raw model ID shown by Groq's live catalog. Otherwise the notebook selects a preferred chat model only if the live catalog lists it, then applies LiteLLM's required `groq/` provider prefix. Model availability depends on the key and may change.

## Run order

1. Run `notebooks/00_start_here.ipynb` for orientation.
2. Run `notebooks/01_loan_approval_governed_walkthrough.ipynb` from top to bottom.
3. Run notebook 02 for group summaries and the counterfactual field-invariance check.
4. Optionally run notebook 03 to make live Groq requests.
5. Run notebook 04 to inspect and visualize every stored GMS triple.

From PowerShell in the project root, the deterministic workflow can also be run with:

```powershell
python loanguard.py
python loanguard.py --rebuild
```

The first build ingests `loan_policy.md` using deterministic regex extraction and creates the local `loan_store/`. The script writes audit and compliance evidence under `out/`. Rebuilding retrains the local GMS representation.

## Knowlytix components used

| Component | Use in this demo |
|---|---|
| Document ingest and GMS/ENM | Store the policy statements and typed numeric policy fields. |
| `ClaimVerifier` | Check facts, numeric claims, comparisons, and application thresholds against policy data. |
| Calibrated thresholds | Derive verifier settings from this small local graph; diagnostics are reported for transparency. |
| `PolicyEngine` | Allow, require, or block proposed assistant actions. |
| `ConstrainedLLM` and `LiteLLMBackend` | Optional Groq-backed generation and claim extraction in notebook 03. |
| `GovernanceTracer` and tracing hardening | Record decisions, seal the event chain, and check for tampering. |
| Compliance evidence and snapshots | Build an evidence package and record run-level artifacts. |
| `ProvenanceRegistry` | Link policy, GMS store, and outputs. |

Application parsing and reporting are ordinary Python/pandas glue. The policy values, typed claims, decision checks, and governance evidence use Knowlytix functions.

## Interpretation and limitations

The example cohort has 12 invented rows. Route-label agreement only confirms consistency with the labels supplied in the synthetic CSV. The group notebook reports counts and a narrow code-path check; it does not calculate statistically meaningful fairness or establish the absence of disparate impact. The GMS corpus is small, so calibrated geometric signals are illustrative rather than validated performance measures; the observed geodesic training accuracy is close to chance and tension calibration is degenerate, so neither should drive applicant decisions. The `dti_percent` field is retained for context but is not a decision rule because the policy defines no DTI threshold. Compliance evidence output is an evidence artifact, not a certification or legal opinion. Every case remains subject to human review.
